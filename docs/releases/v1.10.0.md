# v1.10.0 — assumptions accordion, complex-mode region prefill, a11y metric tooltips

**Released:** 2026-06-17
**Stories/Bugs:** [RPE-119](https://lowermedia.atlassian.net/browse/RPE-119), [RPE-116](https://lowermedia.atlassian.net/browse/RPE-116), [RPE-118](https://lowermedia.atlassian.net/browse/RPE-118), [RPE-117](https://lowermedia.atlassian.net/browse/RPE-117) (closed won't-do)
**Gate:** 965 tests / 68 files (1 env-gated Postgres skip), lint + typecheck + build green.

## Highlights

A UX-polish release for the evaluator, building on the location work from
v1.9.0.

## RPE-119 — simple-mode assumptions accordion

The static "Results estimated using national-average assumptions" note is
now an expandable `<details>` accordion. Collapsed shows the note (with a
"tax & insurance localized to your ZIP" hint when a location is set);
expanded reveals the live baseline values driving the estimate — interest,
term, closing, vacancy, capEx/maint/mgmt/misc %, and the location-adjusted
property tax + insurance — plus the region source label.

## RPE-116 — apply region tax/insurance in complex mode

In complex mode the resolved ZIP was informational only. A non-destructive
**"Apply {state} tax & insurance estimates"** button now appears below the
location input (complex mode, resolved location, purchase price set); one
click fills the property-tax + insurance fixed expenses from the region
rates × price. Explicit action — nothing is overwritten until clicked.

## RPE-118 — keyboard-accessible metric tooltips

The metric descriptions already carried the formula + plain definition
(e.g. cap rate = "NOI ÷ purchase price…") but were exposed only via a
hover-only native `title`. Metric labels are now keyboard-focusable with an
`aria-label` (label + formula/definition) and a focus-visible ring, so
keyboard and screen-reader users reach the content. A visual focus-popover
(vs the native title) remains a possible follow-up.

## RPE-117 — gitSha observability (closed won't-do)

DigitalOcean App Platform builds the api from the Dockerfile on its own
builder and doesn't pass a `GIT_SHA` build arg, so `/v1/health` can't
report the deployed commit without a CI-image pipeline (build in GitHub
Actions → push to DOCR → image-source component). Judged too heavy for the
value; the deployed release is traceable via the git tag, `docs/releases/`,
and the App Platform deploy history. Revisit if per-commit traceability
from the health endpoint becomes important.
